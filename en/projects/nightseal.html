NightSeal PQC

Personal project · Post-quantum · Backup integrity

Problem statement

WriteOnce storage can prevent or restrict rewriting, but by itself it does not provide an autonomous, easily auditable cryptographic proof of the state of a large backup set.

NightSeal builds an exportable proof of file integrity and its evolution over time, with a post-quantum signature layer.

Stack & deployment

  • React/Vite frontend for the dashboard and workflows.
  • FastAPI backend exposing proof and verification operations.
  • Dedicated worker for asynchronous processing.
  • PostgreSQL 16 and Redis 7.
  • Complete deployment through Docker Compose.

Proof chain

1. Inventory — dataset scanning and volume assessment → 2. Manifest — fingerprints and file state → 3. Merkle — compact dataset root → 4. ML-DSA — post-quantum signature → 5. Bundle — verification, audit and reporting.

Manifests can be chained over time so that a previous state becomes part of the cryptographic context of the next one. The end-to-end workflow then generates the proof, signs it and automatically verifies the resulting bundle.

Cryptography

The signing engine includes a demonstration HMAC provider and three real post-quantum profiles: ML-DSA-44, ML-DSA-65 and ML-DSA-87 through pqcrypto. The final configuration uses ML-DSA-65.

Verification is not merely declarative: NightSeal cryptographically verifies the latest signature before considering the proof chain ready.

Implemented features

  • Inventory Scanner and RMAN-like volume scenarios.
  • Manifest generation and temporal chaining.
  • Merkle proofs and post-quantum signatures.
  • Proof bundles and end-to-end verification.
  • Tamper test, self-tests, execution history and audit timeline.
  • Benchmarks, HTML/PDF reports and a production-readiness dashboard.

Docker architecture

React/Vite provides a dashboard for inventory, proof-chain management, audits, simulations and reports. The FastAPI backend orchestrates artifact generation and verification. A worker, PostgreSQL and Redis complete the architecture; datasets, manifests, signatures, reports and histories are mounted in dedicated volumes.

Production readiness

The project contains its own readiness checks: backend availability, accessible dataset, working proof chain, valid manifest chain, active ML-DSA provider and verification of the latest signature.

This separates a prototype that can merely be demonstrated from a state in which critical cryptographic controls actually pass.

Tamper approach

The Tamper Test deliberately modifies an artifact or an element covered by the proof and then reruns verification. This makes the difference between “immutable storage” and “cryptographic integrity proof” directly demonstrable.

Current limitations

Keys & access control: ML-DSA keys are still stored as files. HSM/KMS integration, API authentication and RBAC are not implemented yet.

Enterprise integration: the project currently works with RMAN-like datasets and does not yet include a real Oracle RMAN connector or SIEM export. These are natural next steps toward industrialization.
