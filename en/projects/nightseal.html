NightSeal PQC

NightSeal PQC is a containerized platform designed to simulate and demonstrate a complete integrity-proof chain applied to Oracle RMAN / WriteOnce-style backups. The project combines inventory scanning, chained manifests, Merkle trees, ML-DSA signatures, tamper detection, auditing and report generation.

1. Overview

The project starts from a simple observation: storage immutability and cryptographic proof do not address exactly the same need. NightSeal adds a verifiable and exportable proof layer on top of a large-scale backup environment.

Objective

Produce independent evidence of the state of a backup set, then make it possible to verify later that the files, manifest and proof chain have not been modified.

Approach

The system does not attempt to sign several terabytes directly. It progressively reduces the scope to a compact proof: hashes → manifest → Merkle root → PQC signature → bundle.

2. Proof chain de bout en bout

NightSeal can run each step independently or execute the complete workflow in a single operation. The goal is to keep the chain understandable, verifiable and exportable.

Step 1InventoryDataset scan and file inventory.
Step 2ManifestSHA-256, size, path and context.
Step 3Merkle proofReduction of all hashes to a single root.
Step 4ML-DSAPost-quantum signature of the proof payload.
Step 5Proof bundleAssembly, verification, audit and export.
Important point: manifests are also chained over time. The platform can therefore verify that a manifest history remains consistent and that the expected hash of the previous manifest matches the one actually present.

3. Tamper demonstration

The Tamper Test is one of the most visual parts of the project: NightSeal first verifies a valid proof, deliberately alters the manifest, observes the cryptographic failure, restores the artifact and verifies it again.

This demonstration illustrates the difference between “preventing rewriting” and “being able to cryptographically prove that a state has not been altered.”

4. Simulation engine and policy selection

NightSeal does more than produce a signature. It compares several integrity strategies according to data volume, file count, available throughput, processing window and the desired security level.

P0Hash only
P1Global manifest
P2Dataset manifest
P3Merkle root
P4Per-file signature
P5Block-level integrity

5. Crypto-agility

The engine is not built around a single algorithm. Hash functions and signatures can be compared or replaced to study different trade-offs in performance, security and proof size.

6. Audit, history and reporting

Each execution leaves verifiable artifacts. NightSeal retains workflow history and the timeline of manifests, Merkle proofs, signatures and bundles, then generates a usable report.

The final report consolidates, among other elements, production-readiness status, the active ML-DSA provider, the latest cryptographic verification, the manifest chain and the contents of the proof bundle.

7. What I learned from this project

Cryptographic design

Designing integrity proofs at scale requires distinguishing the data itself, its hash, the compact proof and what actually needs to be signed.

Architecture

The project allowed me to connect the frontend, API, asynchronous processing, storage, Docker volumes and artifact generation within a coherent workflow.

Operational trade-offs

A more granular policy is not always better: it may exceed the backup window, multiply signatures or generate too much metadata.

NightSeal remains a personal demonstration and applied-research project. By itself, it does not replace an enterprise backup architecture, an HSM/KMS, comprehensive access control or a real Oracle RMAN connector.
