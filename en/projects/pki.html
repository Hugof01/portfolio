PQC-OnionPKI

PQC-OnionPKI is an applied engineering project built around a concrete question: how far can a post-quantum trust infrastructure be integrated into a real environment today without modifying traditional clients? To explore this, I built a PKI on a Raspberry Pi, hardened the host, added remote administration through Tor, experimented with a fully post-quantum X.509 chain, and then adapted the architecture to the real limitations of macOS and mail clients. The operational solution therefore keeps a classical trust layer for interoperability while adding an independent ML-DSA-65 signature to outgoing e-mails.

1. Why this project?

The availability of post-quantum algorithms does not mean they can immediately be deployed in existing systems. A PKI is not limited to generating a key pair: it must make certificate formats, trust chains, clients, operating systems, network protocols and widely deployed authentication mechanisms work together.

The actual problem

The project is therefore less about proving that “ML-DSA works” than about studying the transition between a modern cryptographic primitive and a usable infrastructure service. E-mail was deliberately chosen as a difficult use case: it crosses relays, anti-spam policies, metadata transformations and clients that do not always expose the information being transported.

An experimental approach

The incompatibilities encountered are not hidden: they are part of the result. When a theoretically correct architecture cannot be used by macOS or a traditional mail client, the goal is to understand precisely why, then evolve the architecture without losing the intended security property.

2. General architecture

The Raspberry Pi acts as a dedicated host for the PKI and its associated services. This deliberate separation avoids hosting unrelated applications on the trust platform and simplifies hardening, auditing and understanding the security scope.

System layer

  • Raspberry Pi 4 running Debian.
  • Dedicated and hardened SSH, with remote access through a Tor onion service.
  • Network filtering with UFW relying on nftables/iptables-nft.
  • Fail2ban and system hardening settings.
  • Directories and permissions separating cryptographic secrets from application components.

Cryptographic layer

  • OpenSSL for classical PKI operations, CSRs, certificates and TLS.
  • liboqs / OpenSSL-OQS to test post-quantum algorithms in X.509-like workflows.
  • ML-DSA-65 for post-quantum message signatures.
  • Two distinct trust architectures to separate cryptographic feasibility from operational compatibility.

3. The certificate journey: from “full PQC” to a hybrid architecture

This is probably the most important part of the project. The initial idea was to push the experiment all the way: build a fully post-quantum certificate chain. Cryptographically, the experiment works. It is the surrounding ecosystem that then forces the architecture to adapt.

Phase 1 Building a fully post-quantum PKI

A minimal hierarchy of Root CA → Mail CA → application certificates is generated with post-quantum signatures through OpenSSL-OQS/liboqs. Key generation, certificate issuance and cryptographic verification all work.

Phase 2 The first blocker is not cryptographic, but software-related

Once the certificates are produced, the next goal is to use them on a traditional client. This is where the limitation becomes concrete: macOS Keychain and major mail clients cannot natively use this post-quantum X.509 chain. A certificate can be cryptographically valid while still being unusable by the application that is supposed to trust it.

Phase 3 Separating compatibility from post-quantum proof

Rather than forcing an unsupported chain, the architecture is split into two functions: classical certificates remain responsible for interoperability and authentication with the existing ecosystem, while the post-quantum signature becomes an independent proof applied directly to the message.

Phase 4 Provisioning on macOS

A compatible client certificate is exported in a PKCS#12 personal container and then imported into macOS. The trusted CA is installed in Keychain so the client can correctly establish the chain. This preserves a standard user experience for SMTP configuration.

Result A hybrid PKI that is actually usable today

The “full PQC” PKI remains a research artifact demonstrating cryptographic feasibility. The hybrid variant is the one used operationally: classical certificates where clients require them, and ML-DSA-65 where a post-quantum property can be added without breaking interoperability.

This point is central: the hybrid choice is not an abandonment of PQC. On the contrary, it represents a realistic transition strategy: do not require an existing client to understand a format it cannot yet process, while moving the post-quantum property to a layer that I control end to end.

4. Adding a post-quantum signature to e-mails without modifying the client

Once the certificate compatibility problem is isolated, the project focuses on the property actually being sought: providing post-quantum proof of message integrity and authenticity. Integration is performed at the Postfix relay level so that the mail client does not need to implement any PQC-specific logic.

Step 1PostfixReception of the outgoing message on the relay.
Step 2CanonicalisationDeterministic normalization of the message elements to be signed.
Step 3SHA-256Calculation of a stable hash of the canonical representation.
Step 4ML-DSA-65Generation of the post-quantum signature over the proof.
Step 5Réinjection SMTPThe enriched message is reinjected and continues its delivery path.

Why canonicalization?

An e-mail message can undergo representation changes between sending and processing. To verify a signature reproducibly, the system therefore defines a deterministic representation of the covered elements. The same content must produce the same verification payload.

Postfix integration

The signing script is integrated into the Postfix pipeline as a content filter and runs under an unprivileged user. The idea is to move cryptography into the infrastructure rather than requiring a plugin or modification in Apple Mail, Gmail or Outlook.

5. Hardening the host that carries trust

Hosting a PKI on a Raspberry Pi is not enough: the system that stores the keys and performs cryptographic operations becomes part of the trust chain itself. The project therefore includes work on reducing the attack surface and controlling access.

SSH access

Administration uses SSH with a dedicated configuration and client keys. Remote access is also made possible through a Tor onion service to avoid directly exposing an administration interface on a public IP address.

Network filtering

UFW is used as the network filtering management layer, with control over the ports required for operation. Services actually listening on the host are checked in order to limit the exposed perimeter.

Defense in depth

Fail2ban, system hardening settings, permission separation, log inspection and service review complete the protection. The project does not claim to reproduce the guarantees of a certified HSM.

Access through Tor does not replace local hardening. It mainly changes the exposure model: administration can be reached remotely without directly publishing the service IP, while SSH controls, permissions and host protection remain essential.

6. What mail-client testing revealed

After obtaining a correct server-side signature, a second difficulty appears: proof carried in an e-mail is only useful if it survives the delivery chain and can still be retrieved or verified.

Custom headers are not a reliable interface

X-PQC-* metadata can be correctly injected server-side but become invisible, normalized or simply not displayed by Gmail, Apple Mail or Outlook. Cryptographic correctness at the relay therefore does not guarantee visibility to the end user.

The architecture must adapt to the real system

This observation leads to a distinction between proof transported technically and proof exposed to the user. Moving from a header-centered approach to proof that can be made visible in the message content is a direct consequence of integration testing.

This is one of the most interesting lessons from the project: a mechanism can be valid at the primitive level, correctly executed on the server, and still fail to become a truly usable feature because of intermediate protocol or client behavior.

7. What I learned from this project

PQC migration is a systems problem

The algorithm is only part of the problem. Certificates, trust stores, clients, protocols and deployment operations often determine what is actually possible.

A hybrid architecture can be more realistic

Classical / post-quantum coexistence makes it possible to retain legacy dependencies where they are still required while progressively introducing new cryptographic guarantees.

Integration failures are useful

A rejected certificate or a disappearing header is not merely a bug to work around: it directly reveals the maturity of the ecosystem and influences the target design.

Assumed limitations: this is a prototype and an applied-research environment. The keys are not protected by a certified HSM, the physical security of the Raspberry Pi is not comparable to that of an industrial PKI appliance, and the goal is not to present the project as a solution ready to replace an enterprise messaging infrastructure.
