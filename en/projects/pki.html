PQC-OnionPKI

Personal project · Applied cryptography · PKI

Objective

The goal was to go beyond a simple demonstration of a post-quantum algorithm and test PQC as a real infrastructure service: key generation and protection, trust chain, signing, controlled network exposure and integration into an existing application.

E-mail was deliberately chosen as a constrained use case in order to observe the actual limitations of clients, MTAs and legacy formats.

Platform

  • Raspberry Pi 4 dedicated to the PKI and signing service.
  • Debian with SSH hardening, UFW/nftables and Fail2ban.
  • Administrative access through a Tor onion service, without direct public-IP exposure.
  • Private keys isolated from application directories with restrictive permissions.

Trust architecture

100% post-quantum PKI — experimental: a complete Root CA → Mail CA → application-certificate chain was generated with post-quantum signatures through OpenSSL-OQS/liboqs. It is cryptographically functional, but current operating systems and mail clients do not yet natively support post-quantum X.509 certificates.

Hybrid PKI — operational: the compatibility layer remains classical for certificates and SMTP/TLS authentication, while message integrity and authenticity are protected independently with an ML-DSA-65 signature. Existing clients therefore do not need native PQC support.

E-mail signing chain

1. Postfix receives the outgoing message → 2. Canonicalization normalizes headers and the text/plain body → 3. SHA-256 fingerprint via OpenSSL → 4. ML-DSA-65 signature → 5. SMTP reinjection with the proof attached before relaying.

pqc_sign_mail.py is used as a Postfix content_filter and runs as an unprivileged user. The message representation is deterministic so that server-side verification can reproduce the same signed input.

Performance on Raspberry Pi

≈ 19 ms key generation · ≈ 20 ms ML-DSA-65 signing · ≈ 19 ms verification.

These measurements show that post-quantum signing remains compatible with synchronous e-mail processing even on inexpensive ARM hardware.

What the project highlighted

  • PQC X.509 certificates remain incompatible with a significant part of the current client ecosystem.
  • Custom X-PQC-* headers correctly generated server-side can be removed or hidden by Gmail, Apple Mail and Outlook.
  • The proof must therefore be designed at both system and application level, not only at the primitive level.
  • Moving from a proof carried in headers to a visible proof in the content illustrates this adaptation to real-world constraints.

Current intentional limits

The prototype focuses on text/plain messages and deliberately exposes current client limitations. The goal is to document the gap between a cryptographically valid proof and its integration into a legacy ecosystem.
